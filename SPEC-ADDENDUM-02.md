# SPEC-ADDENDUM-02 — Принцип «скрытой информации»: каждый уровень обязан тестировать именно промт

Дополняет `SPEC.md` и `SPEC-ADDENDUM-01.md`. Формулирует общий принцип,
которому должны соответствовать все уровни, и две реализации этого принципа:
через `aiScene` (для уровней на положение элементов — весь текущий каталог) и
через нейтральные «сырые» атрибуты (для будущих уровней на выбор/классификацию
элементов, которых в каталоге сейчас нет).

---

## Проблема

Визуальный отвлекающий элемент (правило B.2 из `SPEC-ADDENDUM-01.md`, например
миска рядом с тарелкой, или кувшинка на картинке у игрока) решает проблему
только для **человека**, который видит картинку, но не видит разметку. ИИ
получает не картинку, а **разметку сцены**. Если эта разметка совпадает с тем,
что видит игрок, и различающий признак закодирован в понятном имени
(`class="plate"` против `class="bowl"`) или просто присутствует в явном виде
(кувшинка на известной позиции), ИИ читает ответ прямо из разметки — промт
игрока почти не имеет значения. Сложность за счёт визуальных обманок не
переносится на ИИ — она существует только в голове у смотрящего на картинку
человека.

## Принцип

**Правильное решение уровня не должно быть выводимо из одной только разметки,
которую получает ИИ.** Обязательно должна существовать информация, которую
видит **только игрок** (через `goal`/визуальную сцену), но которой **нет** в
разметке, уходящей модели, ни в явном, ни в семантически понятном виде — и без
передачи этой информации в промте правильное решение недостижимо даже для
сильного ИИ.

Проверочный вопрос при проектировании уровня:
> Если отдать модели то же, что получает `AiAgent`, вместе с расплывчатым
> промтом вроде «сделай как надо» — сможет ли она случайно угадать решение?
> Если да — уровень не годится.

## Реализация 1 — `aiScene` (уровни на положение элементов, весь текущий каталог)

Каждый уровень в `Data/levels.json` хранит **две** версии сцены:

- `scene` — полная, с кувшинками, для рендера игроку и для валидатора;
- `aiScene` — та же разметка управляемых элементов (пруд, лягушки, клетки
  сетки) **без кувшинок и без любых CSS-правил, определяющих их положение**.

`AiAgent` строит запрос модели только из `aiScene` (раздел 2.4 `SPEC.md`) —
модель никогда не видит, где должна оказаться лягушка; это знает только игрок,
глядя на отрендеренную `scene`, и должен описать это в промте своими словами.
Id управляемых элементов в `aiScene` совпадают с `scene` (иначе CSS,
написанный по `aiScene`, не применился бы к настоящей сцене), но сама
кувшинка и её позиционирующие правила из `aiScene` исключены целиком — это
скрытие через **отсутствие**, а не через нейтральное имя: кувшинке незачем
присваивать «сырой» id, если её не видно вовсе.

Проверено тестами `PromptQuest.Web.Tests/LevelCatalogTests.cs`:
`AiScene_ContainsNoLilyMarkersOrPositionData` (нет упоминаний `lily` ни в
`aiScene.html`, ни в `aiScene.baseCss`, для каждого из 13 уровней) и
`AiScene_OnlyReferencesIdsThatExistInTheRealScene` (всё, что `aiScene`
упоминает по id, существует и в настоящей `scene`).

## Реализация 2 — нейтральные «сырые» атрибуты (будущие уровни на выбор/классификацию)

Для уровня с проверкой `selectorMatches`/`classOnElements` (выбор элементов по
признаку, а не их положение) скрыть «решение через отсутствие», как в
`aiScene`, не получится — сами целевые элементы должны быть видны модели,
иначе по ним ничего не выбрать. Правило для такого случая:

1. **Идентификаторы и классы целевых/отвлекающих элементов должны быть
   семантически нейтральными** (`item-a1`, `elem-7`, `node-3f`), а не называть
   роль элемента (`plate`, `bowl`, `active-flag`).
2. **Различающий признак должен быть «сырым», а не поименованным словом.**
   Вместо `class="small"` — конкретное числовое значение в нейтрально
   названном атрибуте: `data-size="18"` при пороге, который виден только в
   `goal` («выбери самые маленькие — меньше 20»). Вместо `class="plate"` vs
   `class="bowl"` — одинаковый нейтральный класс у всех элементов плюс
   различающий сырой атрибут (например, `data-depth="2"` у плоских,
   `data-depth="14"` у глубоких), а слово «плоская посуда» существует только
   в `goal`, который видит игрок, и должно быть переведено игроком в промте в
   конкретное числовое или структурное условие.
3. **У каждого уровня выбора должен быть путь, которым нельзя решить в лоб по
   названию.** Проверка при ревью: попробовать мысленно (или реально) решить
   уровень, представив, что промт — это одно расплывчатое слово из `goal` без
   уточнений. Если результат случайно совпадает с ожидаемым — сцену нужно
   доработать (сделать признак ещё менее «читаемым» по имени).
4. **Для уровней с вычислением (JS или иначе)** — по той же логике: DOM может
   содержать исходные данные (`data-value`), но не должен содержать имя
   нужной операции в структуре разметки (например, соседний неиспользуемый
   элемент с именем-намёком вроде `class="sum-hint"`). Операция (сумма,
   среднее, максимум и т.п.) должна быть узнаваема только из `goal`.
5. **Правило A из `SPEC-ADDENDUM-01.md` остаётся в силе и становится ещё
   важнее:** AI-вызов не получает `goal` — это единственный канал, через
   который правильная трактовка «сырых» признаков доходит до игрока, а от
   игрока через промт — до ИИ.

## Применимость к текущему каталогу уровней

Весь текущий каталог (раздел 5 `SPEC.md`) — уровни на положение элементов,
покрытые «Реализацией 1» (`aiScene`), активно и для всех 13 уровней. «Реализация
2» (нейтральные атрибуты) пока не применяется ни к одному уровню каталога —
уровней с `selectorMatches`/`classOnElements` сейчас нет; правило остаётся
обязательным для любого такого уровня, если он появится.

## Критерии (дополняют раздел 14 `SPEC.md` — известные ограничения)

- Для каждого уровня `aiScene` не содержит кувшинок/целевых элементов и любых
  данных, по которым выводится положение цели; все id, упомянутые в `aiScene`,
  существуют в настоящей `scene`.
- Ни для одного уровня с выбором/классификацией элементов решение не
  выводимо из разметки, уходящей модели, по семантически понятным именам
  id/класса/атрибута без обращения к тексту `goal`.
- Различающий признак между целевыми и отвлекающими элементами на таком
  уровне закодирован в нейтрально названном атрибуте с «сырым» значением
  (числом, кодом), а не в имени класса/id, совпадающем по смыслу со словом из
  `goal`.
